# Peer Learning Agora

### 내 게임을 보여주고, 동료의 좋은 시도를 발견하고, 다음 사람에게 배움을 건넵니다.

GitHub Pages로 배포한 게임을 서로 플레이하고, **직접 관찰한 긍정적인 사실**을 기록하는 오프라인 피어 러닝 공간입니다. Issue, Assignee, Project, 댓글과 알림을 실제 협업에 사용해봅니다.

> **이 활동은 전원 통과입니다.**
> 게임에 점수나 순위를 매기는 대신, 서로의 시도에서 배울 점을 발견합니다. 게임의 완성도로 합격과 불합격을 나누지는 않지만, 리뷰와 기록, 다음 사람에게 알려주기까지 함께 마무리합니다.

## 처음 참여한다면

1. 내 게임의 **GitHub Pages 주소와 조작법**을 준비합니다.
2. 내 이름과 게임 이름으로 **리뷰 요청 Issue**를 만듭니다.
3. Issue 작성 화면의 **Projects → Edit Projects**에서 **ALEPH Feedback Board**를 선택합니다. 새 이슈는 자동으로 **요청 접수**에 들어갑니다.
4. Assignee를 **bookseal**로 지정합니다. 강사가 요청을 검토하고 동료와 시작 시각을 배정한 뒤 **Todo**로 옮깁니다.
5. 실제 시작 시각에 **In Progress**로 옮기고, 서로 **30분씩** 게임을 살펴봅니다.
6. 각 게임의 이슈에 피드백을 남긴 뒤, **Assignee를 bookseal로 돌려주고 Review로 옮깁니다.**

### Issue를 Project에 연결하는 방법

1. 이 저장소에서 **New issue**를 눌러 리뷰 요청을 작성합니다.
2. 작성 화면의 **Projects → Edit Projects**에서 **ALEPH Feedback Board**를 선택합니다.
3. Issue를 만들면 공유 Project의 **요청 접수**에 자동으로 추가됩니다.
4. 연결 여부는 Issue의 활동 기록과 Project 보드의 카드로 확인할 수 있습니다. 이미 만든 Issue라면 Issue 페이지에서 **Projects → Edit Projects**를 눌러 같은 Project를 추가합니다.

> 이 활동은 기존 조직 Project [ALEPH Feedback Board](https://github.com/orgs/aleph-learner-contributors/projects/1)를 사용합니다. 누구나 볼 수 있는 공개 Project이며, 조직 멤버는 항목과 상태를 편집할 수 있도록 Write 권한이 설정되어 있습니다. 조직 초대를 아직 수락하지 않았다면 수락한 뒤 이용하세요. 보드가 보이지 않거나 담당자·상태를 바꿀 수 없다면 임의로 다른 보드를 사용하지 말고 강사에게 알려주세요.

## 하나의 이슈, 하나의 게임

**내가 만든 이슈는 내 게임의 리뷰 기록입니다.** 상대 게임의 리뷰는 상대가 만든 별도 이슈에 남깁니다.

- **이슈 작성자:** 게임을 만든 학생. 설명하고 질문에 답합니다.
- **Assignee(담당자):** 지금 다음 행동을 해야 하는 사람. 리뷰 중에는 평가자, 배정·최종 확인 단계에서는 bookseal입니다.
- **bookseal(강사):** 짝과 시작 시각을 배정하고, 활동을 최종 확인합니다.

담당자는 게임의 주인이나 점수, 서열을 뜻하지 않습니다. 단계가 바뀌면 기존 담당자를 해제하고 다음 담당자로 넘깁니다.

## 진행 순서

### 1. A가 자기 게임의 리뷰를 요청합니다

A는 아래 양식으로 Issue를 만들고 작성 화면의 **Projects**에서 **ALEPH Feedback Board**를 선택합니다. Issue를 만들면 **요청 접수**에 자동으로 들어갑니다. Assignee는 **bookseal**로 지정합니다.

**제목:** [리뷰 요청] 이름 · 게임 이름

```markdown
## 제작자
이름 / @GitHub계정

## 게임
- 게임 이름:
- GitHub Pages 주소:
- 조작법:

## 소개하고 싶은 시도
어떤 생각으로 만들었는지, 직접 시도한 부분을 짧게 적어주세요.

## 요청 확인
- [ ] 게임 주소가 열리고 플레이할 수 있는지 확인했습니다.
- [ ] ALEPH Feedback Board에 추가했고 요청 접수에 들어간 것을 확인했습니다.
- [ ] Assignee를 bookseal로 지정했습니다.
```

### 2. 강사가 평가자 B와 시간을 배정합니다

강사는 A의 이슈에 **평가자, 시작 시각, 장소**를 댓글로 남기고, Assignee를 **bookseal → B**로 바꿉니다.

요청 검토와 배정이 끝나면 Project 상태를 **요청 접수 → Todo**로 옮깁니다. 실제 리뷰를 시작할 때는 **In Progress**로 옮깁니다. 일정이 맞지 않으면 시작 전에 강사에게 알려주세요.

### 3. B가 A의 게임을 30분 동안 살펴봅니다

A는 게임과 제작 의도를 설명하고, B는 직접 플레이하며 질문합니다. 아래 시간 배분은 권장 예시입니다.

- **5분:** 제작자의 소개와 조작법 설명
- **15분:** 평가자의 플레이와 질문
- **5분:** 관찰한 좋은 점을 함께 이야기하기
- **5분:** 평가자가 이슈에 피드백 작성하기

평가자 B는 **A의 게임 이슈**에 피드백을 남깁니다. 제작자의 설명을 듣는 것에서 그치지 않고 직접 해보세요.

### 4. A가 B에게 GitHub 사용법을 알려줍니다

먼저 리뷰를 받은 A가, 이제 자기 게임의 리뷰를 받을 B에게 다음 과정을 안내합니다.

- 이 저장소에서 새 이슈를 만드는 방법
- 자기 게임의 주소와 소개를 적는 방법
- Project에 이슈를 추가하고 상태를 바꾸는 방법
- Assignee를 지정하고 댓글을 남기는 방법

**A가 대신 작성하지 않고, B가 직접 조작합니다.** B의 새 Issue도 작성 화면의 **Projects**에서 같은 Project를 선택해 **요청 접수 / Assignee: bookseal**로 요청합니다. 강사가 A를 평가자로 지정하고 시작 시각을 안내한 뒤, 준비된 요청을 **Todo**로 옮깁니다.

### 5. 역할을 바꾸어 A가 B의 게임을 30분 동안 살펴봅니다

같은 방법으로 진행하고, 이번에는 A가 **B의 게임 이슈**에 피드백을 남깁니다. 두 방향의 리뷰는 총 60분이며, GitHub 사용법을 알려주는 시간은 별도로 확보합니다.

### 6. 담당자를 강사에게 돌려줍니다

각 평가자는 자신이 맡은 이슈에서 아래 항목을 확인합니다.

- [ ] 상대 게임을 직접 플레이했습니다.
- [ ] 관찰한 긍정적 사실을 피드백 댓글로 남겼습니다.
- [ ] Assignee를 자신에서 **bookseal**로 변경했습니다.
- [ ] Project 상태를 **Review**로 옮겼습니다.

먼저 리뷰를 받은 학생은 다음 학생에게 GitHub 사용법을 알려주는 과정도 마무리합니다. 강사가 활동 기록을 확인한 뒤 **Done**으로 옮기고 이슈를 닫습니다. 강사의 확인 전에는 학생이 이슈를 닫지 않습니다.

**상태의 흐름:** 요청 접수 → Todo → In Progress → Review → Done

## 피드백은 ‘좋은 행동과 구현의 증거’로

이 활동의 피드백에는 **직접 관찰한 긍정적 사실만** 남깁니다. 막연한 칭찬이나 사람에 대한 평가보다, 구체적인 장면을 기록해주세요.

**관찰한 사실 → 좋았던 이유 → 내가 배운 점** 순서로 생각하면 쉽습니다. 배운 점은 실제로 있을 때 적고, 억지로 만들지 않습니다.

> **예시입니다. 실제 리뷰에서는 직접 본 장면을 적어주세요.**
>
> 시작 화면에서 방향키와 점프 키를 함께 안내했습니다. 조작법을 따로 묻지 않고 첫 판을 시작할 수 있었습니다. 나도 내 게임의 첫 화면에 조작법을 넣어보고 싶습니다.

<details>
<summary><strong>피드백 댓글 양식 펼치기</strong></summary>

```markdown
## 피어 리뷰
- 평가자: @GitHub계정
- 진행 시각: YYYY-MM-DD HH:MM ~ HH:MM

### 직접 관찰한 긍정적 사실
어떤 화면, 기능, 설명, 시도를 직접 보았나요?

### 좋았던 이유
그것이 플레이나 이해에 어떤 도움이 되었나요?

### 내가 배운 점 또는 가져가고 싶은 방법 (선택)
내 게임이나 다음 학습에 적용해보고 싶은 점이 있나요?
```

</details>

### 함께 지킬 약속

- **“잘했지만…”으로 지적을 덧붙이지 않습니다.** 피드백을 가장한 비판도 하지 않습니다.
- 학생끼리 비교하거나, 점수·순위·성격 평가를 남기지 않습니다.
- 보지 않은 사실이나 실행하지 않은 경험을 만들어 쓰지 않습니다.
- 관찰할 점이 부족하면 더 플레이하고 질문합니다. 칭찬을 억지로 꾸미지 않습니다.
- 받은 피드백에 답례하거나 즉시 답장할 의무는 없습니다.
- 기술적 문제가 생겨 플레이가 어렵다면 강사에게 알리고 진행 방법을 조정합니다. 오류를 숨기거나 없는 장점을 쓰지 않습니다.

## 댓글과 알림도 협업의 일부입니다

GitHub Mobile을 설치하고 **직접 멘션과 이슈 배정 알림**을 켜두면 담당자 변경과 호출을 확인하는 데 도움이 됩니다. 필요한 상대만 @계정으로 멘션하고, 관련 이슈를 구독해 대화를 확인합니다.

- 시작 시각은 **강사의 댓글과 오프라인 안내**를 기준으로 합니다.
- 댓글에 시각을 적는 것만으로 예약 알람이 설정되는 것은 아닙니다.
- Working Hours는 알림을 받을 시간대 설정이지, 특정 시각의 알람 예약 기능이 아닙니다.
- 모바일 알림은 보조 수단입니다. 수업 밖에서 즉시 응답할 의무는 없습니다.

## 활동 자체에 대한 의견은 따로 남겨주세요

이 공간의 운영 방법이나 GitHub 실습에 대한 질문·제안은 **[운영 의견] 제목의 별도 이슈**로 남길 수 있습니다. 긍정적 사실 피드백 원칙이 운영상의 문제 제기를 금지한다는 뜻은 아닙니다.

ALEPH 과제·학습 플랫폼의 오류나 개선 제안은 [aleph-feedback](https://github.com/aleph-learner-contributors/aleph-feedback/issues)에 남깁니다. 사람에 관한 민감한 내용은 공개 이슈 대신 강사에게 비공개로 전달해주세요.

## 공개 공간 안내

이 저장소의 게임 링크, 이름, 계정명, 이슈와 댓글은 인터넷에 공개됩니다. 수업 안내에 따라 이름을 적되, 공개를 원치 않으면 작성 전에 강사와 비공개로 상의해주세요.

전화번호, 이메일, 학번, 비밀번호, API 키, 비공개 과제 링크나 허가받지 않은 다른 사람의 자료는 올리지 않습니다. GitHub Pages 주소도 공개해도 되는 자신의 게임 주소만 공유합니다.
